# Astra computer-use and structured-tool execution paths

Investigated 2026-09-05 for [Establish Astra computer-use and structured-tool execution paths](https://github.com/Flow-Fly/pixel-forge/issues/590), under [Teach agents to improve Pixel Forge animations with UI control and structured tools](https://github.com/Flow-Fly/pixel-forge/issues/589).

Repository baseline: `develop` at `07bc075b82e040738d696a3b33b702bb810b08a1`. This is documentation and read-only inspection, not a working experiment or a new product decision. Official documentation describes capabilities and rollout; it does not establish access for this account.

## Answer

Astra has documented computer-use and structured-tool capabilities. A comparison is technically plausible in a host that connects both to the same isolated browser project. No complete Astra + Pixel Forge hybrid path was exercised here. In particular, generic MCP support does not establish Astra WebMCP support, and operating Pixel Forge through mouse/keyboard does not automatically apply its Automation Session permissions, attribution, or Pause behavior.

The accepted [Agentic Preview specification](https://github.com/Flow-Fly/pixel-forge/issues/523), [Editor Command API and Automation Adapter decision](https://github.com/Flow-Fly/pixel-forge/issues/441), and [public Site Tool Facade scope](https://github.com/Flow-Fly/pixel-forge/issues/553) remain authoritative: structured, browser-gated editing is the product contract. UI experiments can inform a later decision; success alone would not revise that contract.

Preserve an independent source copy and each partial result in the later experiment; verify recovery before depending on it.

## Implications for the pending decisions

Three arrangements remain candidates rather than selected environments:

1. **One API harness and isolated browser profile per attempt.** Keep Astra/model settings fixed; expose only UI actions, only policy-gated editor tools, or both. This is the clearest way to control tool availability, but requires account access and a reviewed experiment harness. A general code executor with page/store access would defeat an enforced UI-only condition.
2. **One desktop host for all attempts.** Verify Astra selection, UI access, and a working policy-gated structured connection to the same project. WebMCP alone is not yet documented evidence for Astra; local MCP requires the missing bridge. Host permission controls must cover screenshots and UI actions as well as structured calls.
3. **T3 collaborative browser.** Tool metadata makes a browser experiment plausible, but page initialization, gesture coverage, visibility, and structured connection remain untested. A direct adapter invoked through `preview_evaluate` would be a development experiment with different authority, not a demonstrated external transport.

For any candidate, the later human decision should define the permitted observation channels, who controls approval, how to halt all action paths, sequential handling of UI/structured writes, and evidence retained for UI actions that lack automation provenance. Use separate copies of one source revision and preserve editable outputs. Host/tool availability can be checked before paid creative runs; no unavailable transport should silently fall back to broader access.

This research resolves what is supported, what exists in the inspected code, and where evidence is missing. It does not choose the host, approve an authority exception, execute the comparison, or judge animation quality.
